# 为什么我还是先选 Markdown

在准备给个人站做后台之前，我还是先保留了本地 Markdown 这种方式。

原因很现实：

- 写文章足够快
- 不依赖后台
- 内容能直接跟着项目一起管理
- 很适合个人阶段先把内容积累起来

这类方案最适合当前这种状态：

- 站点还在持续调整
- 内容量还不算特别大
- 自己一个人维护为主

# 当前内容系统的结构

目前内容主要分成两类：

- `src/blog/post`：技术文章
- `src/blog/weekly`：日常记录

这两类内容本质上都还是 Markdown，只是通过目录来区分不同类型。

然后在读取时，再统一转换成前端使用的数据结构。

# 一篇文章包含什么

当前每篇文章的结构都比较简单，主要分成两部分。

## 1. frontmatter

也就是文件顶部的元信息。

比如：

```md
---
title: 使用 Markdown 构建个人网站内容系统
date: 2026/05/15
desc: 记录当前个人网站如何使用本地 Markdown 组织文章与日常
tags: ['#全部', '#Markdown', '#内容系统']
cover: https://example.com/cover.png
---
```

这部分主要负责提供列表页和详情页需要的摘要信息。

## 2. 正文内容

frontmatter 下面就是正文 Markdown。

正文里目前支持：

- 标题层级
- 图片
- 引用
- 代码块
- GFM 语法
- 少量 HTML
- `[[toc]]` 目录占位

这对个人写技术文章来说已经够用了。

# 当前这套方案的优点

## 1. 内容和代码放在一起，维护成本低

对于个人项目来说，内容和代码在一个仓库里，其实是有优势的。

因为每次更新文章时，不需要切到另一个系统里去处理。

而且文章本身也可以纳入版本管理。

## 2. 对写作者很友好

Markdown 的好处一直都很稳定：

- 可读性强
- 迁移成本低
- 不容易被某个编辑器绑定
- 后面切数据库也仍然可以继续存 Markdown 正文

也就是说，Markdown 并不会因为以后接后台就失去价值。

## 3. 很适合先把展示层搭起来

当前站点最重要的一步，是先把：

- 文章列表
- 文章详情
- 日常列表
- 日常详情

这些基础内容页面跑通。

本地 Markdown 正好适合作为第一阶段的数据源。

# 这种方案的问题是什么

本地 Markdown 方案虽然好用，但它并不是最终形态。

主要问题在几个方面。

## 1. 不方便在后台直接管理

如果以后想要：

- 新建文章
- 编辑文章
- 删除文章
- 改标签
- 控制草稿和发布状态

那仅靠本地 Markdown 会越来越不方便。

## 2. 上线后同步流程不够直观

如果线上仍然直接读文件，那每次新增或删除文章，都要关心：

- 文件有没有同步到服务器
- 页面有没有重新构建
- 当前内容是不是最新的

这对于后续维护来说会越来越麻烦。

## 3. 容易和数据库方案冲突

如果后面接了 MySQL，又继续让线上直接读本地文件，就会有“双份数据源”的问题。

这也是为什么后面一定要明确“谁才是真源”。

# 我更推荐的演进方式

当前最适合的思路不是立刻抛弃 Markdown，而是给它换一个角色。

也就是：

- 现在：Markdown 是前台直接读取的数据源
- 以后：Markdown 变成导入源

推荐未来的链路是：

`Markdown -> 导入器 -> MySQL -> NestJS API -> Next.js`

这样一来，Markdown 仍然保留了写作优势，但线上展示只认数据库。

# 为什么这个方向更合理

## 1. 写作习惯不用变

如果我还是喜欢本地写 Markdown，那后面也不用强制切成后台富文本。

只要后台支持导入就行。

## 2. 线上数据可以统一管理

MySQL 成为线上真源后，前台和后台都只通过接口访问同一份数据。

这样不会出现：

- 前台读的是文件
- 后台改的是数据库

这种两边不一致的问题。

## 3. 后续扩展能力会更强

一旦切到数据库，后面想加这些功能就自然很多：

- 草稿
- 发布
- 置顶
- 推荐
- 标签管理
- 批量导入
- 操作日志

# 这套内容系统最重要的设计原则

我现在越来越觉得，个人内容站点最重要的不是“数据存在哪里”，而是“内容流转是否清晰”。

只要下面这条链路是清楚的，系统就不会太乱：

- 内容从哪里来
- 怎么被校验
- 怎么进入数据库
- 前台从哪里读
- 后台从哪里改

把这件事想清楚之后，很多技术选择其实都会变得容易。

# 结尾

Markdown 不是落后的方案，它只是更适合放在不同阶段扮演不同角色。

对现在这个个人网站来说，它依然是一个很好的起点。

而后面真正要做的，是把这套内容系统平滑地升级成一个更适合长期维护的结构。
